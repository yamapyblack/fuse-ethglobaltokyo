# Fuse

An NFT gacha: lock two away for good, an AI fuses them into one. Rerolling burns what you pulled.

- Chain: Base
- Storage: Cloudflare R2
- Image generation: OpenAI image edit API (both parent images go in, one fused image comes out)
- Hosting: Vercel

> **This branch (`v2`) is the version being built for sale, and is not deployed yet.**
> The ETHGlobal Tokyo hackathon version is on `main`, tagged `hackathon-submission`.
> It used a different model (parents locked in a pool, 0.001 ETH, 26 starter pieces) and is still
> live on Base Sepolia.

## The rules

**Genesis.** 1,000 pieces at 0.05 ETH: 13 creatures, 13 sushi and 13 Japanese lucky charms.
Every Genesis piece has the same Umami of 50, so nothing about the mint is a better or worse draw.
The sale opens in batches — `saleCap` starts at zero and the owner raises it, so a batch that sells
out is a batch that sold out, rather than a thousand pieces sitting unsold on chain. The cap can
only ever go up.

**Fusing.** Pick two NFTs you own and pay 0.005 ETH. Both parents spend one of their three fusion
charges, and a new child is minted to you. When a piece spends its third charge it is burned in the
same transaction — it is gone, not moved. The child's artwork is generated by an AI from both parent
images.

**Reminting.** Not happy with the child? Remint burns it and rolls a new one from the same two
parents. It is free apart from gas, capped at three per child, and there is no side-by-side
comparison, no history and no undo. Exactly one result is ever on screen.

Supply grows slowly: a fusion spends two charges and creates a piece worth three, so the collection
gains one piece for every three fusions.

## No rarity, on purpose

There is exactly one number on an NFT — Umami — and no tiers, no jackpot rolls and no weighted drop
rates. Genesis pieces are all 50. A child's Umami is a uniform roll from 1 to 100 that is **not**
inherited from its parents, so there is no breeding strategy that produces better pieces.
Every trait value is equally likely.

This is a deliberate legal posture, not an oversight: a paid mechanic with clearly better and worse
random outcomes is the part that gets a Japanese operator in trouble. **Do not add rarity tiers,
weighted drops or stat inheritance** because they would make the collection more exciting.

Generation is the one scarcity axis that survives, and it is fine: Gen 0 is finite and only the
people who bought the mint have it, but which generation you hold is decided by what you chose to
fuse, never by chance.

## Layout

```
contracts/   Foundry. FuseNFT / Fuse
web/         Next.js (App Router). Three screens + backend API + the generation scripts
```

### Two contracts

| Name | Role |
| --- | --- |
| `FuseNFT` | One ERC-721 holding both Genesis pieces and fused children, with 5% royalties (ERC-2981). Only `Fuse` can mint, burn or set a tokenURI |
| `Fuse` | The Genesis sale, `fuse()`, `remint()` and `finalizeMetadata()`. Holds the fusion charges, the lineage of every child, and the seed each child's attributes are derived from |

There is no pool contract and **no approval step**: fusing never transfers a parent, so `fuse()` is
a single transaction with nothing to approve first.

Three separate authorities:

- **owner** (deploy key): opens the sale, sets the Genesis families, withdraws, rotates the metadata signer
- **metadataSigner** (backend key): `finalizeMetadata` only. It cannot mint, burn or withdraw
- **anyone**: mint at 0.05 ETH, fuse at 0.005 ETH, remint for free

### Attributes are derived, not stored

A child stores its seed and its lineage; everything else is computed from them.

```
umami  = 1 + seed % 100
mood   = (seed >> 16) % 5      accent = (seed >> 32) % 6
charm  = (seed >> 48) % 8      pose   = (seed >> 64) % 5
```

`web/src/lib/traits.ts` repeats these formulas for the frontend and the generator. **If you change a
bit shift or the length of a trait list, change both** or the chain and the artwork stop agreeing.

Genesis families are packed two bits per token, so all 1,000 fit in eight words. Genesis *traits* are
not on chain at all — the artwork was generated ahead of time and the metadata JSON is the source of
truth, which is why `traitsOf()` reverts for Genesis instead of inventing values.

### Generation flow

```
[browser] fuse() -> child NFT is minted as Pending
        | after the tx lands: POST /api/generate { tokenId }
[server]  read childInfo(tokenId) from chain
        -> do nothing unless it is Pending (this is the only ticket in)
        -> take a generation lock in R2 (conditional write, so concurrent calls collapse to one)
        -> read both parent images from R2 by tokenId, snapshot them, fuse with OpenAI, store in R2
        -> send finalizeMetadata(tokenId, url) as the metadata signer
[browser] poll GET /api/status?tokenId= every 4s and render the result
```

Vercel cannot host a long-running worker, so instead of an event listener the browser pokes the
server and the server verifies the claim against the chain. Nothing the caller says is trusted: the
only way in is a tokenId that somebody paid to put into `Pending`.

Parent images are resolved **from R2 keys, never from `tokenURI`**. A parent can be burned in the
same transaction that creates the child, so by the time generation runs it may no longer exist on
chain. The snapshot copy is what makes a remint reuse the same two source images years later.

### Why a failed generation never costs extra

`state/{requestId}.json` tracks attempts and progress, and every step checks whether it is already
done: image already in R2, chain already Ready. A timed-out generation resumes without a second
payment or a second mint. R2 conditional writes are the lock, so concurrent calls collapse into one.
Automatic attempts are capped at 5; the screen offers an explicit retry that bypasses the cap.

## Setup

### 1. Run the contract tests

```bash
cd contracts && forge test
```

### 2. Create an R2 bucket and make it public

Enable the **Public Development URL**, add a **CORS policy** allowing `GET`/`HEAD` from `*` (the
selection screen fetches metadata JSON from the browser), and create an **R2 API token** with
**Object Read & Write** — write-only breaks the checks that keep a retry from calling OpenAI again.
`R2_ACCOUNT_ID` is the subdomain of the bucket's S3 API endpoint.

### 3. Build the Genesis allocation

```bash
cd web && pnpm install
pnpm exec tsx scripts/build-genesis.ts
```

Writes `scripts/genesis.json` (1,000 pieces) and `scripts/genesis-families.json` (the eight packed
words). Every axis is distributed as evenly as it divides, and duplicate trait combinations are
swapped out, so no combination is designed to be rare. The shuffle is seeded, so re-running produces
the same allocation.

### 4. Generate the artwork

```bash
pnpm check:r2        # verify R2 connectivity first (does not call OpenAI)
pnpm gen:genesis     # 1,000 images -> R2. Re-runs skip what already exists
```

OpenAI rate-limits image generation to a handful per minute, so a full run takes hours. It is
resumable and safe to interrupt. Each image is flattened onto the background colour before upload,
because the API sometimes returns transparency and a half-transparent collection does not look like
a set.

### 5. Deploy

```bash
cd contracts
cp .env.example .env   # DEPLOYER_PRIVATE_KEY, METADATA_SIGNER_ADDRESS, GENESIS_BASE_URI
set -a && source .env && set +a
forge script script/Deploy.s.sol:Deploy --rpc-url https://sepolia.base.org --broadcast --verify
```

`GENESIS_BASE_URI` is the R2 prefix the Genesis tokenURIs point at, e.g.
`https://pub-xxxxxxxx.r2.dev/genesis/` — keep the trailing slash.

### 6. Load the Genesis families, then open the sale

```bash
cd web
pnpm setup:genesis                            # writes the eight words and verifies them
SALE_CAP=200 OPEN_SALE=1 pnpm setup:genesis   # only once the verification passes
```

Do not skip the verification. If the families are not loaded, every Genesis piece reads as Creature
and every child's lineage is wrong from the first fusion onwards.

### 7. Run it

```bash
pnpm build && pnpm start
```

`pnpm dev` shows Next's dev indicator, which ends up in screen recordings.

## Screens

1. `/mint` — the Genesis sale: price, minted count, remaining, up to 10 per transaction
2. `/` — pick two of your NFTs and fuse. Each card shows how many fusions it has left, and the last
   one is flagged, because the third fusion burns it
3. `/result/[tokenId]` — generation status, the single result, and Remint behind a burn confirmation

All on-screen text is English. While a transaction is in flight the screen links to it on BaseScan.

## Known limitations

- **Vercel's Hobby plan caps functions at 60s** while generation takes 30–60s, so it can time out.
  The run resumes from the state record at no extra cost
- Generation does not start while the page is closed. Reopening the result page resumes it
- The image model is swappable via `OPENAI_IMAGE_MODEL` (default `gpt-image-1`)
- If the deploy wallet is an EIP-7702 delegated smart account, `_safeMint` invokes
  `onERC721Received` on it and gas estimates from the public RPC can fall short. The scripts double
  their estimate; if a wallet transaction fails with "out of gas", raise the limit by hand
